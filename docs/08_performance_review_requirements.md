## 1. 目的・背景

### 1.1 背景

既存の `jinij` 人事システムは、従業員情報管理・休暇申請・勤怠・給与といった運用業務を電子化している。しかし、従業員の**定期的な人事評価**（四半期・半期・年次）を管理する機能が存在しないため、評価結果は別ファイルや紙で管理されており、過去の評価履歴の参照や評価状況の可視化が困難な状態にある。

### 1.2 目的

人事評価機能を `jinij` へ追加することで、以下を実現する。

- 評価者（マネージャー・人事担当）が従業員の評価を一元的に登録・管理できる
- 被評価者（従業員）が自身の評価結果をシステム上で確認・承認できる
- 評価の提出時に通知を自動送信し、確認漏れを防止する
- 評価履歴を蓄積し、昇給・昇格判断の根拠データとして活用できる

---

## 2. 対象ユーザー・利用シーン

| ユーザー | 利用シーン |
|---|---|
| 人事担当（hr） | 全従業員の評価レコードの登録・確認・削除。評価状況の一括把握 |
| 管理者（admin） | hrと同等の操作に加え、システム全体の管理 |
| マネージャー（manager） | 担当部署の従業員に対する評価の作成・編集・提出 |
| 従業員（employee） | 自身の評価結果（提出済み・確認済み）の閲覧、確認済みステータスへの更新 |

---

## 3. 業務要件（機能要件）

| 機能ID | 機能名 | 概要 | 対象ロール |
|---|---|---|---|
| F-80 | 評価一覧表示 | 評価レコード一覧を表示。従業員・年度・種別・ステータスでフィルタリング可能 | 全ロール（表示範囲はRLSで制御） |
| F-81 | 評価新規登録 | 従業員・評価年度・種別・各スコア・コメントを入力して評価レコードを作成 | hr, admin, manager |
| F-82 | 評価編集 | draft ステータスの評価レコードを編集 | hr, admin, manager |
| F-83 | 評価提出 | draft → submitted へのステータス変更。被評価者へ通知を自動送信 | hr, admin, manager |
| F-84 | 評価確認（本人確認） | submitted → acknowledged へのステータス変更（被評価者のみ操作可） | employee（自身のみ） |
| F-85 | 評価詳細表示 | 各評価レコードの全項目を確認できるモーダル表示 | 全ロール（閲覧権限の範囲内） |
| F-86 | 評価削除 | draft ステータスの評価レコードを削除 | hr, admin |

### 3.1 評価項目

| 項目 | 内容 | 型 |
|---|---|---|
| 評価年度 | 対象年（例: 2026） | 整数 |
| 評価種別 | quarterly（四半期）/ semi_annual（半期）/ annual（年次） | ENUM |
| 四半期 | quarterly の場合のみ Q1〜Q4 | 整数（NULL可） |
| 総合評価 | 1〜5の5段階（1=S卓越〜5=D不十分） | 整数 |
| 業績評価 | 目標達成・成果に関するスコア（1〜5） | 整数 |
| 行動評価 | 行動指針・協働姿勢に関するスコア（1〜5） | 整数 |
| スキル評価 | 専門スキル・成長に関するスコア（1〜5） | 整数 |
| 目標達成状況 | 期中目標に対する達成状況（自由記述） | TEXT（NULL可） |
| 強み | 評価期間中の優れた点（自由記述） | TEXT（NULL可） |
| 改善点 | 評価期間中の課題（自由記述） | TEXT（NULL可） |
| 次期目標 | 次の評価期間における目標（自由記述） | TEXT（NULL可） |
| 評価者コメント | 評価者からの総合コメント（自由記述） | TEXT（NULL可） |
| 本人コメント | 被評価者からの振り返りコメント | TEXT（NULL可） |

### 3.2 評価ステータス遷移

```
draft（作成中）
  → [hr/admin/manager が提出] → submitted（提出済み）
      → [employeeが確認] → acknowledged（確認済み）
```

- `draft` → `submitted`: 評価者ロールによる操作。被評価者へ通知が自動送信される
- `submitted` → `acknowledged`: 被評価者本人のみ操作可能

## 4. 非機能要件

| 区分 | 要件 |
|---|---|
| 性能 | 評価一覧は500件以下を想定。ページロード2秒以内 |
| セキュリティ | RLSにより役割ごとの閲覧・操作範囲を厳密に制御。employeeは自身の提出済み・確認済み評価のみ参照可 |
| 可用性 | Supabase クラウドのSLA（99.9%以上）に準拠 |
| 整合性 | 同一従業員・同一評価期間（year + type + quarter）の重複を DB UNIQUE 制約で防止 |
| 通知 | 評価提出時に DB トリガー経由で被評価者のユーザーへ通知を自動生成 |
| 監査 | 作成者・作成日時・更新日時を記録。updated_at はトリガーにより自動更新 |

---

## 5. 制約条件

| 制約 | 内容 |
|---|---|
| DB制約 | 同一 (employee_id, review_year, review_type, review_quarter) の UNIQUE 制約 |
| スコア制約 | 各スコアは 1〜5 の整数のみ。DB CHECK 制約で保証 |
| 年度制約 | review_year は 2000〜2100 の範囲 |
| 削除制約 | draft ステータスのみ削除可能。submitted/acknowledged は削除不可（UI制御） |
| quarterly 制約 | review_type = 'quarterly' の場合、review_quarter (1〜4) が必須 |

## 6. 前提条件・前提システム

| 前提 | 内容 |
|---|---|
| 認証 | Supabase Auth による JWT 認証が完了していること |
| 従業員データ | employees テーブルに評価対象従業員が登録済みであること |
| 通知システム | `004_notifications.sql` で定義した notifications テーブルが存在すること |
| ロール管理 | profiles テーブルの role カラムに hr/admin/manager/employee が設定されていること |

## 7. スコープ

### 対象範囲

- 人事評価レコードの CRUD（登録・参照・更新・削除）
- 評価ステータスのワークフロー管理（draft → submitted → acknowledged）
- 評価提出時の自動通知
- 役割に応じたアクセス制御（RLS）

### 除外範囲

- 評価スコアを用いた昇給・昇格の自動計算
- 360度評価（同僚評価）
- 評価テンプレートのカスタマイズ機能
- 評価データの CSV エクスポート（将来拡張候補）
- 評価傾向の統計・グラフ表示（将来拡張候補）

## 8. 用語定義・略語一覧

| 用語 | 定義 |
|---|---|
| 人事評価 | 従業員のパフォーマンスを定期的に評価する業務プロセス |
| 評価者 | 評価を作成・提出する側のユーザー（マネージャー・人事担当） |
| 被評価者 | 評価の対象となる従業員 |
| draft | 評価者が作成中のステータス。まだ被評価者には見えない |
| submitted | 評価者が提出済みのステータス。被評価者が閲覧・確認可能になる |
| acknowledged | 被評価者が内容を確認済みとしたステータス |
| 四半期評価 | 1年を4つに分けた Q1〜Q4 単位の評価 |
| 半期評価 | 1年を2つに分けた上期・下期単位の評価 |
| 年次評価 | 1年単位の評価 |
| RLS | Row Level Security。PostgreSQL の行単位アクセス制御機能 |
