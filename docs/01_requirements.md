## 1. 目的・背景

### 1.1 背景

中小企業において、従業員の情報管理・休暇申請の承認業務はメールや表計算ソフトによって属人的に行われているケースが多い。手作業による管理は情報の散逸、承認漏れ、集計ミスを招き、人事担当者の工数を圧迫している。

### 1.2 目的

本システム `jinij` は、従業員情報の一元管理と休暇申請の電子化・ワークフロー化を実現し、以下を達成することを目的とする。

- 人事担当者・管理職の業務工数を削減する
- 従業員の休暇申請・承認状況をリアルタイムで可視化する
- 権限に応じた情報アクセス制御を実現し、情報漏洩リスクを低減する
- 通知機能により承認状況を即時に関係者へ伝達する

## 2. 対象ユーザー・利用シーン

### 2.1 対象ユーザー

| ロール | 説明 | 人数規模 |
|---|---|---|
| **employee（一般従業員）** | 自身の情報確認・休暇申請 | 数十〜数百名 |
| **manager（管理職）** | 部下の休暇申請承認・部署内情報閲覧 | 数名〜数十名 |
| **hr（人事担当）** | 全従業員情報の管理・休暇申請のプロキシ申請 | 数名 |
| **admin（システム管理者）** | 全機能へのアクセス・マスタ管理 | 1〜3名 |

### 2.2 主な利用シーン

| シーン | 対象ロール | 概要 |
|---|---|---|
| 休暇申請 | employee | 休暇の種別・期間を選択して申請する |
| 休暇承認 | manager / hr / admin | 申請中の休暇をレビューし承認または却下する |
| 従業員情報の閲覧・更新 | hr / admin | 従業員の基本情報・雇用情報を管理する |
| ダッシュボード確認 | 全ロール | 人事状況のサマリーをリアルタイムで確認する |
| 通知受信 | employee | 申請結果（承認/却下）を通知として受け取る |
| データエクスポート | hr / admin | 従業員情報を CSV でエクスポートする |

## 4. 非機能要件

### 4.1 性能要件

| 項目 | 目標値 |
|---|---|
| 画面初期表示 | 3秒以内（一覧画面） |
| API レスポンス | 95パーセンタイルで 1 秒以内 |
| 同時接続数 | 100ユーザー |
| CSV エクスポート | 1,000件を 5 秒以内 |

### 4.2 セキュリティ要件

| 項目 | 内容 |
|---|---|
| 認証方式 | Supabase Auth（JWT ベース） |
| アクセス制御 | PostgreSQL Row Level Security (RLS) による DB レベル制御 |
| 通信暗号化 | HTTPS 必須（TLS 1.2 以上） |
| JWT 検証 | Rust バックエンドで全 API リクエストを検証 |
| 個人情報保護 | 従業員の個人情報は本人および権限者のみ参照可能 |

### 4.3 可用性要件

| 項目 | 目標値 |
|---|---|
| 稼働率 | 99.5%（月間） |
| 計画停止 | 深夜帯（0:00〜5:00）のみ |
| データバックアップ | Supabase の自動バックアップ機能を利用 |

### 4.4 運用性要件

| 項目 | 内容 |
|---|---|
| ログ | Rust バックエンドで `tracing` による構造化ログ出力 |
| 監査ログ | audit_logs テーブルに操作履歴を記録 |
| エラー通知 | 将来的に Sentry 等への連携を想定 |

## 8. 用語定義・略語一覧

| 用語 / 略語 | 定義 |
|---|---|
| 部署コード | `departments.code`。半角英数字・ハイフンで構成される部署の識別コード（例: DEV, HR） |
| 出勤打刻 | `attendance_records.clock_in`。出勤時刻の記録操作 |
| 退勤打刻 | `attendance_records.clock_out`。退勤時刻の記録操作 |
| 休憩時間 | `attendance_records.break_minutes`。休憩時間（分）。実働時間算出時に差し引く |
| 実働時間 | `(clock_out - clock_in) - break_minutes` で算出される実際の勤務時間 |
| 勤怠ステータス | `attendance_records.status`。present / absent / late / early_leave / holiday / remote のいずれか |
| 基本給 | `salary_records.base_salary`。月次の基本賃金 |
| 残業手当 | `salary_records.overtime_pay`。時間外労働に対する手当 |
| 各種手当 | `salary_records.allowances`。通勤手当・住宅手当等の合計 |
| 控除合計 | `salary_records.deductions`。社会保険料・税金等の控除合計 |
| 手取り | `salary_records.net_salary`。基本給 + 残業手当 + 各種手当 − 控除合計 で算出される支給額 |
| 支払日 | `salary_records.paid_at`。給与振込日 |
| 評価軸 | 人事評価で使用する5つの評価項目（業績・チームワーク・コミュニケーション・リーダーシップ・成長） |
| 評価スコア | 各評価軸に対して付与する 1〜5 の整数点。1=改善要、2=要努力、3=標準、4=優秀、5=卓越 |
| 総合スコア | 5軸スコアの算術平均（小数第2位まで）。DB Generated Column として自動算出 |
| 四半期 | 1年を3ヶ月ごとに区切った期間。Q1（1-3月）、Q2（4-6月）、Q3（7-9月）、Q4（10-12月） |
| draft | 評価レコードの初期ステータス。編集可能な下書き状態 |
| submitted | 評価者が提出した状態。hr / admin による確定を待つ |
| finalized | hr / admin が確定した状態。以降は変更・削除不可 |
| RLS | Row Level Security。PostgreSQL の行単位セキュリティポリシー |
| JWT | JSON Web Token。認証に使用するトークン形式 |
| BaaS | Backend as a Service。Supabase が該当 |
| 有給残日数 | `annual_leave_balance`。年次有給休暇の残日数 |
| プロキシ申請 | hr / admin が従業員に代わって行う休暇申請 |
| 承認待ち | `pending` ステータスの休暇申請 |
| アプリ内通知 | メール等外部チャネルを使用せず、システム画面上で表示する通知 |
| Realtime | Supabase の WebSocket ベースリアルタイム機能 |
