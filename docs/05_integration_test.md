# 結合テスト仕様書

**システム名**: jinij — 社内人事管理システム
**バージョン**: 1.0
**作成日**: 2026-03-30
**対象機能**: 人事評価管理（F-80〜F-88）

---

## 1. テスト方針

| 項目 | 内容 |
|---|---|
| 目的 | Vue コンポーネント ↔ Composable ↔ Supabase の連携動作を検証する |
| 対象インターフェース | `EvaluationView.vue` ↔ `useEvaluations.ts` ↔ Supabase DB |
| テスト環境 | ローカル Supabase（`supabase start`）または Staging 環境 |
| 前提条件 | マイグレーション `007_evaluations.sql` 適用済み、シードデータあり |

---

## 2. テスト対象インターフェース

| # | 連携箇所 | 概要 |
|---|---|---|
| IF-01 | `EvaluationView` → `useEvaluations.fetchRecords()` | フィルタ変更時に一覧取得を呼び出す |
| IF-02 | `EvaluationView` → `useEvaluations.createRecord()` | モーダル保存時に登録APIを呼び出す |
| IF-03 | `EvaluationView` → `useEvaluations.updateRecord()` | 編集モーダル保存時に更新APIを呼び出す |
| IF-04 | `EvaluationView` → `useEvaluations.changeStatus()` | 提出・確定ボタン押下時にステータス変更を呼び出す |
| IF-05 | `EvaluationView` → `useEvaluations.deleteRecord()` | 削除ボタン押下・確認後に削除APIを呼び出す |
| IF-06 | `useEvaluations` → Supabase（RLS） | ロール毎に参照・操作可能な範囲が正しく制限される |
| IF-07 | Router → `EvaluationView` | `requiresManager: true` のガードが正しく動作する |
| IF-08 | `AppSidebar` → Router | manager/hr/admin のみサイドバーに「人事評価」が表示される |

## 3. テストケース

### IT-01: 評価一覧表示（フィルタ連携）

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-01 |
| **前提条件** | hr アカウントでログイン済み。評価レコード5件（2026年Q1×3件、2025年Q4×2件）登録済み |
| **テスト手順** | 1. `/evaluations` を開く → 2. 年度フィルタを「2026年」に設定 → 3. 絞り込みボタン押下 |
| **期待結果** | テーブルに2026年の評価3件のみ表示される |
| **データ整合性** | 表示される `year` 列が全て `2026` |

### IT-02: 新規評価登録フロー

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-02 |
| **前提条件** | manager アカウントでログイン済み。従業員「田中太郎」が存在する |
| **テスト手順** | 1. 「新規評価登録」ボタン押下 → 2. 従業員を「田中太郎」選択 → 3. 年度=2026, Q1, 全スコア=3 入力 → 4. 「登録」ボタン押下 |
| **期待結果** | モーダルが閉じ、テーブルに新規レコードが追加される |
| **データ整合性** | `evaluation_records` テーブルに `employee_id=田中太郎のID, year=2026, quarter=1, status='draft'` のレコードが存在する |

### IT-03: 同一期間の重複登録防止

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-02, IF-06 |
| **前提条件** | 「田中太郎」の2026年Q1の評価レコードが既に存在する |
| **テスト手順** | 同一の従業員・年度・四半期で再度登録を試みる |
| **期待結果** | エラーアラートが表示される（DB UNIQUE 制約違反） |
| **データ整合性** | `evaluation_records` に重複レコードが存在しない |

### IT-04: 評価提出ワークフロー

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-04 |
| **前提条件** | manager アカウントでログイン済み。draft ステータスの評価が1件存在する |
| **テスト手順** | 1. 対象レコードの「提出」ボタン（送信アイコン）押下 → 2. 確認ダイアログで「OK」 |
| **期待結果** | ステータスバッジが「下書き」→「提出済み」に変わる |
| **データ整合性** | DB の `status = 'submitted'` に更新される |

### IT-05: 評価確定ワークフロー（HR 専用）

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-04 |
| **前提条件** | hr アカウントでログイン済み。submitted ステータスの評価が1件存在する |
| **テスト手順** | 1. 対象レコードの「確定」ボタン（チェックアイコン）押下 → 2. 確認ダイアログで「OK」 |
| **期待結果** | ステータスが「確定」に変わり、編集・削除ボタンが無効化される |
| **データ整合性** | DB の `status = 'finalized'` に更新される |

### IT-06: finalized レコードの編集不可

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-03, IF-06 |
| **前提条件** | finalized ステータスの評価レコードが存在する |
| **テスト手順** | 対象レコードの「編集」ボタンが無効（disabled）になっていることを確認 |
| **期待結果** | 編集ボタンが `disabled` 状態で押下不可 |
| **データ整合性** | DB の `finalized` レコードは変更されない |

### IT-07: ロール制御 — employee は評価を参照のみ

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-06, IF-07 |
| **前提条件** | employee アカウントでログイン済み |
| **テスト手順** | `/evaluations` に直接アクセスする |
| **期待結果** | `requiresManager` ガードにより `/` (ダッシュボード) にリダイレクトされる |
| **データ整合性** | - |

### IT-08: サイドバーのロール別表示

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-08 |
| **前提条件** | 各ロールでログイン |
| **テスト手順** | employee / manager / hr / admin の各ロールでログインし、サイドバーを確認する |
| **期待結果** | employee: 「人事評価」リンクなし / manager・hr・admin: 「人事評価」リンクあり |
| **データ整合性** | - |

### IT-09: 総合スコアの自動計算

| 項目 | 内容 |
|---|---|
| **対象IF** | IF-02 |
| **前提条件** | hr アカウントでログイン済み |
| **テスト手順** | 1. 新規登録フォームで全スコアを 4, 3, 5, 2, 4 に設定 → 2. 登録 |
| **期待結果** | 一覧の「総合」列に `3.6` が表示される |
| **データ整合性** | DB の `overall_score = 3.60`（Generated Column）と一致する |
